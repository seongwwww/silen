# 실사용 E2E 점검 기록 (2026-07-30)

`main` `c7d3925`에서 시작. 신규 익명 사용자로 **실제 API + 실제 Vertex** 호출만
써서 전 기능을 훑었다. DB 직접 INSERT는 추출·임베딩 큐를 건너뛰어 실사용과
달라지므로 쓰지 않았다.

## 데이터

`POST /api/memories`로 15일치(7/15~7/29)를 `occurredAt`과 함께 넣었다.
회사(매일) · 운동(어제까지 매일, 오늘 없음) · 카페(14일 만에 재등장) ·
김밥(3일 연속) · 감정(대체로 좋음/그냥, 오늘만 별로).

## 발견과 수정

### 1. 쿠키 없는 클라이언트는 매 요청마다 새 사용자를 만든다 — 미수정

`Authorization: Bearer`를 보내도 라우트는 **쿠키만** 본다. 15번 호출하니 사용자가
15명 생겼다. 브라우저는 쿠키를 들고 다니므로 실사용엔 문제가 없지만, 비브라우저
클라이언트는 기록이 조용히 흩어진다.

**미수정으로 둔다.** 지금은 본인용 브라우저 도구이고, Bearer 수용은 인증 표면을
넓히는 변경이라 별도 판단이 필요하다.

### 2. `run_regenerations`가 요청 없이도 일기를 만들었다 — 수정

주기마다 무조건 `generate_diary`를 불러, **마감 탐지가 끝나기 전에 차이 0건짜리
일기가 굳었다.** 실제로 차이 20건이 탐지됐는데 일기엔 0건이었다.
"탐지 성공을 일기 예약의 조건으로 둔다"는 앞선 수정이 이 경로로 우회되고 있었다.

→ 대기 중인 요청이 있는 사용자만 처리한다(`fetch_regenerate_requests`).
→ 재실행 결과: `run_daily`(차이 3, 서술 3) → `run_scheduled` 순서로 바뀌었고
   일기 `다른점` 섹션에 차이가 들어갔다.

### 3. 주간 리포트가 내부 수치를 노출했다 — 수정

> "최근 7일 평균 **0.29**, 해당 날 **1.00** (z=1.6)"

일별 서술에서 이미 라벨로 바꾼 결함이 주간 경로에만 남아 있었다. 게다가
`_persist_slot`이 **이미 있는 차이를 그대로 재사용**해, 규칙을 고쳐도 옛 문구가
영원히 남았다.

→ 주간 감정 설명을 공용 `emotion_label`로 바꾸고, 재사용 시에도 설명·점수를
   갱신한다(`refresh_difference_description`). 사용자의 확인·기각은 건드리지 않는다.
→ 화면 확인: "최근 감정을 남긴 7일은 주로 '그냥'이었고, 이 날은 '좋음'"

### 4. 일기의 "오늘 처음" 제목이 내용과 어긋났다 — 수정

그 목록에 부재("운동이 없네요")·재등장·감정이 함께 들어가는데 제목은 "오늘 처음"
이었다. → **"함께 찾은 것"**.

### 5. (오탐) 과거 날짜가 재탐지되지 않는 것처럼 보였다 — 버그 아님

`differences`만 지우고 다시 돌렸더니 과거 차이가 안 생겼다. 큐가 이미 비어
`recalculate_if_past`가 다시 돌 일이 없었을 뿐이다. 메모를 직접 재계산하니
7/27 김밥이 `first_occurrence`로 정상 생성됐다.

**단, 예외를 `logger.warning`으로 삼키는데 CLI는 `print` 기반이라 그 로그가
보이지 않는다.** 재계산이 실패해도 조용하다.

### 6. 주간 감정 서술이 지난 날을 "오늘"이라 불렀다 — 수정

7월 22일 기록인데 "오늘은 감정을 좋음으로 기록했습니다"라고 나왔다.

원인이 둘이었다.
- 탐지 설명 자체가 `"오늘은 '좋음'"`이었다. 이 설명은 과거 날짜로도 다시
  계산되므로 날짜 중립이어야 한다 → `"이 날은"`
- 가드레일이 없었다 → `is_today`를 호출자가 넘기고, 오늘이 아닌데 "오늘"이
  들어가면 폐기한다. UTC로 비교하면 자정 경계에서 틀리므로 사용자 타임존으로
  판정해 넘긴다

→ 결과: "2026년 7월 22일에는 '좋음'을 남겼습니다"

### 7. 일반명사가 주간 슬롯으로 올라왔다 — 일부만 수정

"이번 주 처음 기록한 것"이 **"일"** 이었다(`회사 일이 많았다`).

`몸`·`길`만 불용어에 넣었다. **`일`·`집`은 그대로 둔다** — 기존에 "과잉 차단이
더 나쁘다"고 의도적으로 제외했고 그 테스트가 있다. 실사용 근거가 하나 생겼을
뿐이라 결정을 뒤집지 않았다. 사람이 판단할 항목이다.

## 남은 의심

- 발견 1(쿠키 없는 클라이언트)
- **"일"·"집" 불용어 여부** — 실사용에서 "일"이 주간 발견으로 올라왔다.
  기존 결정을 존중해 두었으니 사람이 정해야 한다.
- **재계산 실패가 조용하다** — `logger.warning`이 CLI 출력에 안 보인다.
- 엔티티 차이 설명도 `"오늘 기록에는 없음"`처럼 "오늘"을 쓴다. 감정만 고쳤다.
  과거 재탐지에서 같은 문제가 날 수 있다.

## 단계 A 구현 — 사진 검색

`photo_embeddings`(1408, HNSW cosine)를 따로 둔다. 텍스트 임베딩과 차원이 달라
한 인덱스에 섞을 수 없다(ADR-0004의 "서로 다른 모델·차원을 한 인덱스에 섞지
않는다"를 그대로 따른다).

- 저장·검색·**교차 사용자 격리**·**잠금 반영**·**삭제 연쇄** 통합 4건 통과
- 실제 사진 2장으로 DB 교차 검색 확인: "노란 원"→해, "초록 잔디밭"→땅

## 단계 C(사진 엔티티 → 탐지)의 채택 기준 — 결정

사진 엔티티에는 텍스트 추출의 앵커("추출 name이 원문에 없으면 폐기")가 없다.
그래서 **다음 틀을 통과한 것만 채택하고 나머지는 폐기한다.**

1. **사용자 언어 앵커** — 그 사용자의 활성 기록 어딘가에 **텍스트로 등장한 적
   있는 말**만 채택한다. 사진에서만 보이고 사용자가 한 번도 쓴 적 없는 말은 버린다.
2. **기존 불용어** — 텍스트와 같은 목록을 적용한다.
3. **출처 표시** — 채택해도 근거에 "사진에서"를 남긴다. 사용자가 판단할 수 있어야 한다.
4. **탐지 수식 불변** — 놀라움 계산은 그대로다. 입력 엔티티 집합만 넓힌다.
   LLM에게 "차이를 찾아줘"라고 시키지 않는다.

이 틀이 없으면 사용자가 쓴 적도 없고 검증도 안 된 말로 차이 카드가 뜬다.


## 단계 B·C 구현 — 캡션과 사진 엔티티

**B. 캡션** — `gemini-3.5-flash`가 "보이는 명사만" 적게 하고, 통과분을
`assets.extracted_text`에 둔다. **`memories.raw_text`에 섞지 않는다**
(원본 ↔ AI 생성물 분리). 검색용 본문은 `raw_text + 캡션`으로 만든다.

이걸로 **사진만 남긴 기록이 처음으로 검색에 걸린다.** 지금까지는 `raw_text`가
비어 임베딩 자체가 생기지 않아 통째로 사라졌다.

캡션 가드레일: 빈 값·120자 초과·**추측 표현**(`같다`·`듯`·`보인다`·`아마` 등)은
폐기한다. 사진에서 감정이나 상황을 읽어내면 과잉해석이 된다.

**C. 사진 엔티티** — 앞서 정한 틀을 그대로 구현했다.

1. 캡션에 대해 기존 추출 가드레일(이름이 캡션에 실재) 적용
2. **사용자 언어 앵커** — 그 사용자가 **텍스트로 쓴 적 있는 말**만 채택
3. 기존 불용어 동일 적용
4. 탐지 수식 불변 — 입력 엔티티 집합만 넓어진다

실측: 해 그림 하나를 처리하니 캡션 `"원, 도형"`이 나왔고, **엔티티는 0개**였다.
사용자가 "원"·"도형"을 쓴 적이 없어 앵커가 정확히 걸러냈다. 앵커가 없었다면
사용자가 쓴 적 없는 말로 차이 카드가 떴을 것이다.

**통합 8건 통과**: 저장·검색·교차 사용자 격리·잠금 반영·삭제 연쇄 ·
원본 미오염 · 사진만 있는 기록의 검색 본문 · 앵커 · 추측 차단.


## 회고에 사진 검색 합치기

**사진은 LLM이 고르지 않는다.** 인용 가드레일이 원문 대조를 요구하는데 사진만
있는 기록은 대조할 원문이 없다. LLM이 그걸 고르면 **응답 전체가 폐기**된다.
그래서 벡터 순위 그대로 결정적으로 덧붙이고 인용은 비운다 — 지어낸 문장이
생길 여지가 없다.

**유사도 임계 0.065.** 실측에서 맞는 짝은 +0.085~+0.107, 무관한 짝은
+0.016~+0.046이었다. 임계가 없으면 관련 없는 사진이 모든 답변에 딸려 붙는다.
실제로 "카페 언제 갔지"에 무관한 사진 3장이 붙는 것을 보고 넣었다.

검증:

| 질문 | 결과 |
|---|---|
| 초록 잔디밭 | 사진 1장 (맞는 것만) |
| 카페 언제 갔지 | 인용 2건, **사진 0장** (무관한 사진 제거) |
| 화성 탐사선 | 아무것도 없음 |

**오탐 하나:** 앱에서 `photoUrl`이 비어 보였다. 코드 문제가 아니라 내가
`assets` 행만 만들고 Storage에 실물을 안 올린 테스트 데이터 탓이었다.
실물이 있는 사진에서는 정상이다. 서명 URL은 실물이 없으면 만들어지지 않는다.

**남은 것:** 회고 응답이 21초대다(질문 임베딩 2회 + 검색 + LLM). 사진 임베딩이
늘어난 만큼 더 느려졌다.


## 회고가 21초 걸리던 이유 — 단계별 실측

| 단계 | 시간 |
|---|---:|
| 클라이언트 생성(텍스트) | 0.70초 |
| 클라이언트 생성(멀티모달) | 3.06초 |
| 질문 임베딩(텍스트) | 4.23초 |
| 질문 임베딩(멀티모달) | 2.21초 |
| 벡터·키워드·사진 검색 | 0.02초 |
| 클라이언트 생성(선택기) | 0.88초 |
| **LLM 근거 선택** | **12.31초** |

원인 셋이었다. DB는 무관했다(0.02초).

1. **모델이 사고 과정을 켜고 돌았다.** 근거 고르기는 추론이 아니라 선택인데
   기본값이 켜짐이었다. 실측: 기본 5.82/2.31/2.98초 → `thinking_budget=0`
   0.87/1.09/1.21초. **3배**
2. **요청마다 클라이언트를 새로 만들었다** — 연결 설정에만 4.6초.
   임베딩을 같은 클라이언트로 반복하니 3.72초 → 0.34초였다
3. **두 임베딩이 순차였다.** 서로 무관한 네트워크 호출이라 병렬로 돌린다

결과: **21초 → 2.8~14초**(보통 4~8초). 편차가 큰 것은 Vertex 왕복 지연이고,
선택 결과가 많을수록(8건) 생성이 길어져 느리다.

**남은 레버:** `location=global` 라우팅. 한국에서 `asia-northeast3`가 더 가까울
수 있으나 모델 가용성이 달라 확인이 필요하다.
