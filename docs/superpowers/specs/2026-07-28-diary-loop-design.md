# 일기 루프 완성 설계 스펙 (기획서 §6)

> 상태: 확정. 다음 단계: 구현 계획(`docs/superpowers/plans/2026-07-28-diary-loop.md`).
> 기획서 §6 "일기 생성 루프"의 빠진 조각을 채운다 — 초안 수정·확정, 톤, 다시 만들기.

## 1. 문제

일기가 **생성만** 된다. 사용자는 고칠 수도, 톤을 정할 수도, 다시 만들 수도 없다.
기획서 §6이 한 덩어리로 서술한 루프가 반쪽이다:

> 초안 → 인라인 수정 or 바로 확정. 안 건드리면 draft 보존
> 톤 조절 3층: ①기본 설정 ②생성 전 주문 ③생성 후 대화형 수정
> 늦은 메모 → "다시 만들기" 1회(자동 재생성 X)

`diaries.edited_text`·`status`·`style_profile` 컬럼은 **이미 있는데 아무도 쓰지 않는다.**
워커는 톤을 `담백`으로 하드코딩한다.

## 2. 상태 전이

```
draft ──수정──> edited ──확정──> confirmed
  └──────── 바로 확정 ────────┘
confirmed ──되돌리기──> edited
```

- **안 건드리면 `draft` 보존**(기획서 문구 그대로).
- `lib/services/difference.ts`의 `assertValidTransition` 패턴을 그대로 따른다.
- **TOCTOU 방어**: 기대 상태(`expected`)와 함께 원자적으로 업데이트해 0행이면 실패로 본다(`differenceRepository.updateStatus` 선례).

## 3. 톤 — 실질 2층

기획서는 3층이지만, "요청을 남기고 다음 생성이 반영"하는 구조에서 ②(생성 전 주문)와 ③(생성 후 대화형 수정)은 **같은 메커니즘**이 된다. 실질 2층으로 구현한다.

| 층 | 저장 위치 | 언제 반영 |
|----|-----------|-----------|
| **① 기본 프리셋** | `users.style_profile`(이미 있음) | 매 생성 시 자동 |
| **②③ 재생성 주문** | `diaries.tone_instruction`(신규) | 다음 생성 시 **1회** |

- 프리셋은 **담백 · 따뜻** 둘. 프롬프트 초안 §4가 같은 입력에 두 톤 예시를 든다.
- 자유 주문은 재생성 쪽이 담당한다(프리셋을 늘리지 않는다).
- ⚠️ **사실은 고정, 문체만 바뀐다**(기획서 §4-9). 톤이 바뀌어도 사실 집합은 그대로여야 하며, 기존 가드레일(근거 정합·메타 표현·엔티티 표현)을 **그대로** 적용한다.

## 4. 다시 만들기 — 명시적 1회

1. 사용자가 버튼을 누른다.
2. **편집본(`edited`/`confirmed`)이면 "고친 내용이 사라집니다"를 알리고 한 번 더 확인받는다.**
3. `diaries.regenerate_requested_at`을 기록한다(선택적으로 `tone_instruction`도 함께).
4. 다음 `run-diary`가 **`status` 무관하게** 재생성한다.
5. 처리하면 **요청을 비운다.** 자동 재생성이 아니다 — 다시 만들려면 다시 눌러야 한다.

즉시 반영하지 않는다. 지금은 사람이 `run-diary`를 직접 돌리는 단계이고, F4(스케줄)가 붙으면 자동으로 반영된다.

## 5. 스키마 — 마이그레이션 1개

`diaries`에 컬럼 둘을 추가한다. up/down 동봉.

| 컬럼 | 용도 |
|------|------|
| `tone_instruction text` | 다음 생성에 1회 적용할 자유 주문. 처리 후 비운다 |
| `regenerate_requested_at timestamptz` | 재생성 요청 시각. 처리 후 비운다 |

`users.style_profile`은 이미 있으므로 추가하지 않는다.

## 6. 화면 · API

| 경로 | 역할 |
|------|------|
| `/diary` | 본문 **인라인 편집** · 확정 · 다시 만들기(경고) |
| `/settings` (신규, 최소) | 톤 기본 프리셋 선택 |
| `PATCH /api/diaries/[id]` | `edited_text` 저장 · 상태 전이 |
| `POST /api/diaries/[id]/regenerate` | 재생성 요청(+ 주문) |
| `PATCH /api/users/me` | `style_profile` |

- 설정 화면은 **톤 프리셋만** 둔다. `diary_time`은 F4에서 붙인다.
- API는 세션 클라이언트 + RLS를 쓴다(`service_role` 금지).

## 7. 워커

`generate_diary`가:
- **① 사용자 프리셋을 읽어** 프롬프트 톤에 반영한다(지금 `담백` 하드코딩을 교체).
- **② `tone_instruction`이 있으면** 프롬프트에 주문을 더한다.
- **`regenerate_requested_at`이 있으면** `status`와 무관하게 재생성하고, 저장 후 두 필드를 **비운다**.
- 요청이 없으면 지금 동작 그대로다(하루 1건 멱등·자동 재생성 금지).

## 8. 테스트

### 8.1 단위 (DB·LLM 없음)
- 상태 전이 규칙: 허용 전이 통과 · 금지 전이 거부.
- 프롬프트 조립: 프리셋·주문이 프롬프트에 들어간다.
- 일기 화면: 편집 → 저장 · 확정 버튼 · 다시 만들기 경고(편집본일 때만).
- 설정 화면: 프리셋 선택.

### 8.2 통합 (실 DB)
- `PATCH`가 `edited_text`와 상태를 바꾸고, **기대 상태가 다르면 실패한다**(TOCTOU).
- 타 사용자 일기를 수정할 수 없다(RLS).
- 재생성 요청이 저장되고, `generate_diary`가 **status 무관 재생성 후 요청을 비운다**.
- 요청이 없으면 기존 멱등 동작(재호출 no-op)이 그대로다.
- 사용자 프리셋이 프롬프트에 반영된다(스텁 writer로 확인).

### 8.3 eval
톤이 바뀌어도 **사실 집합이 그대로인지**(기획서 §4-9 "문체 자유·사실 고정") 골든셋에 케이스를 더한다.

## 9. 범위 밖

- 즉시 반영(큐·폴링·처리중 UI).
- `diary_time` 설정·알림(F4).
- 일기 버전 보관·되돌리기 히스토리.
- 프리셋 3개 이상 · 온보딩에서의 톤 설정(F6).

## 10. 주요 결정 요약

- **상태 전이는 `difference` 선례 그대로** — 순수 검증 함수 + TOCTOU 방어.
- **톤은 실질 2층** — 기본 프리셋(사용자) + 재생성 주문(일기, 1회). ②③이 같은 메커니즘이라 합친다.
- **사실 고정·문체만 변경** — 기존 가드레일을 그대로 적용한다.
- **다시 만들기는 명시적 1회** — 편집본이면 경고 후 덮어쓰고, 처리하면 요청을 비운다.
- **즉시 반영하지 않는다** — 요청을 남기고 다음 생성이 반영한다.
- 마이그레이션은 `diaries` 컬럼 2개뿐.
