# 통합 테스트 격리 설계 스펙

> 상태: 확정(브레인스토밍 승인). 다음 단계: 구현 계획(`docs/superpowers/plans/2026-07-28-test-isolation.md`).
> 원칙 한 줄: **테스트는 DB를 소유하지 않는다.**

## 1. 문제

통합 테스트가 로컬 개발 DB의 **다른 데이터를 파괴한다.** 실데이터로 파이프라인을 검증하려면 테스트를 못 돌리고, 테스트를 돌리면 검증 재료가 사라진다. 실제로 이 세션에서 **두 번** 재료를 잃었다.

**파괴자는 두 곳뿐이다.** 나머지 테스트는 이미 자기가 만든 사용자만 지운다(`deleteUser(alice)`·`delete_user(user_id)`).

| 위치 | 무엇을 |
|------|--------|
| `lib/repositories/schema.integration.test.ts:22-26` | `beforeEach`마다 `listUsers` → **모든 auth 사용자 삭제** |
| `lib/repositories/queue.integration.test.ts` · `worker/tests/test_process.py` · `worker/tests/test_extraction_integration.py` | **`memory_jobs` 큐 전체 purge**(총 8곳) |

### 왜 그렇게 짜였나

- **schema 테스트**: 스키마 제약(cascade·삭제 원장)을 검사하느라 "깨끗한 상태"를 원했다. 하지만 **단언은 이미 `where user_id = $1`로 스코프돼 있다**(`schema.integration.test.ts:198`). 전역 삭제는 습관이지 필요가 아니다.
- **큐 테스트**: 전역 큐를 공유하니 격리하려고 purge했다. 그리고 `"처리 후 큐가 비었다"`처럼 **전역 상태를 단언**한다.

## 2. 원칙

테스트는 **자기가 만든 것만 만들고, 자기가 만든 것만 지우고, 자기 것에 대해서만 단언한다.**

## 3. `schema.integration.test.ts` — 전역 사용자 삭제 제거

- `beforeEach`의 `listUsers` → 전부 `deleteUser` 하는 블록을 **없앤다.**
- 테스트가 만든 user id를 모아 두고 **그것만** 정리한다.
- `delete from public.deletions`도 그 user id들로 한정한다. 단언이 이미 user 스코프라 전역 비움이 필요 없다.

## 4. 큐 — purge 제거 + 남의 메시지 보호

**purge만 없애면 더 위험해진다.** `process_pending`이 큐 머리부터 읽어 **남의 메시지도 소비하고 삭제**하기 때문이다. 테스트는 스텁 추출기를 주입하므로, 남의 실데이터 잡이 엔티티 없이 처리되고 **조용히 사라진다** — 이번에 두 번 당한 그 경로다.

### 해결: `process_pending(only_user_id=...)`

- 메시지 페이로드의 `user_id`가 다르면 **아무것도 하지 않는다.** 삭제도 아카이브도 하지 않고 건너뛴다.
- 건너뛴 메시지는 읽기 때문에 visibility timeout(60초) 동안 안 보이지만 그 뒤 되돌아온다. **무해하다.**
- 아카이브(데드레터)는 `except` 절에서만 일어나므로, 건너뛴 메시지가 데드레터로 가지 않는다.
- 테스트는 자기 user id를 넘긴다 → **purge가 불필요해진다.**
- `only_user_id`가 `None`이면 지금과 동일하게 전부 처리한다(프로덕션 기본 동작 불변).

이 파라미터는 테스트 편의만이 아니다. 향후 `run-pending --user <id>` 디버깅의 훅이 된다(노출은 이번 범위 밖).

## 5. 전역 단언 → 자기 것 단언

테스트를 **약화하는 것이 아니라 정확하게** 만드는 변경이다. "큐가 비었다"는 우연히 참인 전역 상태이고, "내 메시지가 사라졌다"가 실제로 검증하려던 것이다.

| 지금 | 바꿀 것 |
|------|---------|
| `read_messages(...) == []` — "처리 후 큐가 비었다" | **내 `memory_id`를 참조하는 메시지가 없다** |
| 큐 메시지 개수 확인 | **내 `memory_id`를 참조하는 메시지가 있다** |

## 6. 검증

### 6.1 기존 회귀
통합 테스트가 전부 그대로 통과해야 한다(프론트 49 · 워커 131 기준선).

### 6.2 핵심 회귀 — 이 작업의 증거
**큐에 "남의" 메시지를 미리 넣어두고 통합 테스트를 돌려도 그 메시지가 살아남는다.**

- 테스트에 속하지 않는 user/memory를 참조하는 메시지를 큐에 넣는다.
- 워커 통합 테스트를 돌린다.
- 그 메시지가 **여전히 큐에 있다**(삭제·아카이브되지 않았다).

이 테스트가 없으면 회귀가 조용히 돌아온다.

### 6.3 사람이 확인할 것
통합 테스트를 돌린 뒤 기존 사용자·메모·일기가 남아 있는지. 지금은 사라진다.

## 7. 범위 밖

- 테스트 전용 DB·Supabase 스택 분리.
- 검증 데이터 seed 스크립트(`supabase/seed.sql` 훅은 설정돼 있으나 파일 없음).
- `run-pending --user` CLI 노출.
- 워커 CLI UTF-8 · 엔티티 추출 일반명사 억제(별개 문제).

## 8. 주요 결정 요약

- **테스트는 DB를 소유하지 않는다** — 자기 것만 만들고 지우고 단언한다.
- `schema` 테스트의 **전역 사용자 삭제를 제거**한다. 단언이 이미 user 스코프라 안전하다.
- **큐 purge를 제거**하되, 그것만으로는 더 위험하므로 `process_pending(only_user_id=...)`로 **남의 메시지를 보호**한다. 건너뛸 뿐 삭제·아카이브하지 않는다.
- **전역 상태 단언을 자기 것 단언으로** 바꾼다. 약화가 아니라 정확화다.
- **"남의 메시지가 살아남는다" 회귀 테스트**가 이 작업의 증거다.
