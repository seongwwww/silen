## 0. 이 설계를 관통하는 판단

기존 설계의 치명적 결함은 **차이를 보여줄 수 있을 때까지 사용자가 받을 보상이
약하다**는 점이었다.
차이를 주인공으로 두면 baseline이 쌓이기 전엔 화면이 비고, 일기 앱 이탈은
대부분 3일 안에 일어난다. 7일째의 보상은 오지 않는다.

그래서 **주인공을 바꾼다.**

| | 무엇이 | 언제부터 |
|---|---|---|
| **매일의 보상** | **일기** — 흩어 쓴 메모를 한 편으로 묶어준다 | **Day 0** |
| 첫 발견 | **기록에서 뜸해진 것·오랜만** — 놓치기 쉬운 변화 | Day 3부터 |
| 두 번째 보상 | **주간 리포트** — 모아야 보이는 반복·빈도 | Day 7 |

보상이 계단으로 온다. 7일은 기다림이 아니라 세 번째 계단이다.

**검증 질문은 7일이 아니라 3일이다:** *3일 안에 "어, 이건 몰랐네"가 한 번
나오는가?* 단, Day 3은 제품 가설이지 탐지 정확도를 희생해서 맞출 마감일이 아니다.

## 1. 무엇을 차이로 보여줄 것인가

### P1. 매일과 주간의 역할을 나눈다

사용자가 **이미 아는 것**을 되돌려주면 발견이 아니다. 사흘 연속 김밥을 먹은 걸
모르는 사람은 없다. 놓치기 쉬운 것은 셋이다 — **기록에서 뜸해진 것**,
**오랜만인 것**, **흩어져 있어 못 묶는 것**.

| 화면 | 무엇을 | 왜 |
|---|---|---|
| **매일 카드** | **기록 부재 · 오랜만** | 사용자가 놓치기 쉽다 |
| **주간 리포트** | 반복 · 빈도 · 연속 | 오늘 말하면 뻔하지만 모아 보면 발견이 된다 |

**연속(streak)은 매일 카드에서 빠진다.** 주간으로 간다.

### "부재"의 진실성 경계

짧은 메모에 어떤 단어가 없다고 해서 실제 생활에서 그 행동을 하지 않았다는 뜻은
아니다. 따라서 이 제품이 탐지하는 것은 **생활의 부재가 아니라 기록의 부재**다.

- 오늘 활성 메모가 1개 이상일 때만 계산한다. 빈 날에는 부재를 만들지 않는다.
- 확률의 분모는 달력의 모든 날이 아니라 **메모를 남긴 활성일**이다.
- UI·LLM은 반드시 *"오늘 기록에는 운동 얘기가 없었어요"*처럼 말한다.
- *"오늘 운동하지 않았어요"*처럼 생활 사실로 승격하는 문장은 가드레일에서 거부한다.
- 근거에는 과거 해당 엔티티 메모와 오늘의 활성 메모 ID를 함께 연결한다.

### P2. 놀라움(surprisal)이 유일한 순위 기준

first_occurrence·freq_shift·zscore를 각각 다른 척도로 다루면 정렬이 불가능하다.
전부 **bits** 하나로 환산한다.

```
과거 활성일 D = target 이전 28일 중 메모가 1개 이상인 날
관측일수  n = |D|
등장일수  k = D 중 해당 엔티티가 등장한 날
등장확률  p = (k + 0.5) / (n + 1)               # 0/무한대 방지 평활
오늘 등장  surprisal = -log2(p)
오늘 부재  surprisal = -log2(1 - p)
```

오늘은 확률 추정에서 제외한다. 그래야 오늘 관측을 확률 계산과 점수 계산에
이중으로 쓰지 않는다. 기록 부재는 과거 활성일에 자주 언급되던 것이 오늘의
활성 기록에 없을 때만 상위가 된다.

예시:

| n, k | 오늘 | bits | 해석 |
|---|---|---:|---|
| 2, 2 | 기록에 없음 | 2.58 | 앞선 두 활성일에 있던 언급이 오늘 기록에 없음 |
| 7, 6 | 기록에 없음 | 2.42 | 대부분의 활성일에 있던 언급이 오늘 기록에 없음 |
| 14, 1 | 등장 | 3.32 | 드물게 기록되던 것이 다시 등장 |
| 7, 7 | 등장 | 0.09 | 늘 기록되던 것이 오늘도 등장 |

**임계값 2.0 bits.** 그 아래는 뻔한 것이므로 버린다.

### P3. 하루 최대 3개

기획서 §5의 "하루 1~3개". 상한이 없으면 목록이 되고, 목록은 발견이 아니다.

### P4. 첫 등장은 저장하지만 차이 카드로 올리지 않는다

"처음"이 여섯 개 뜨는 화면은 발견이 아니라 사전이다. 첫 등장은
**"오늘 처음" 목록**으로 내리고, 그중 사람이 있으면 **꼬리 질문 한 개**를 건넨다.
(이미 구현됨 — `diary_sections.section_type='질문'`)

`first_occurrence` 레코드는 일기 질문과 주간 리포트의 근거이므로 계속 저장한다.
제외되는 것은 **매일 카드 랭킹과 서술 호출**뿐이다.

## 2. 감정축을 두 번째 탐지 축으로 채택한다 (신규)

**지금 감정을 수집하는데 아무도 쓰지 않는다.** API가 받아 `emotions`에 저장까지
하는데(`memoryRepository.ts:29`), 워커에 `emotion` 참조가 0건이다.

명사 목록("빵빠레 처음")과 **"평소 감정 기록 범위에서 크게 벗어났어요"는
급이 다르다.**
데이터 경로가 이미 완성돼 있으므로 쓰기만 하면 된다.

```
baseline  최근 활성일의 일별 평균 valence → 평균 mu, 표준편차 sd
오늘      v = 오늘 메모들의 평균 valence
sd_eff = max(sd, 0.25)       # 이산값(-1, 0, 1)의 0분산 방어
z = (v - mu) / sd_eff
p = 2 * (1 - Φ(|z|))         # 양측 꼬리확률
surprisal = -log2(max(p, 2^-8))
```

- 과거에 감정이 기록된 활성일이 최소 **5일**이어야 계산한다
- 오늘의 감정 메모와 baseline에 사용한 감정 메모를 evidence로 연결한다
- 같은 방향 연속은 매일 카드가 아니라 주간 리포트에서 다룬다
- `detection_method='zscore'`, `category='감정전환'` — **둘 다 스키마에 이미 있다**

⚠️ **과잉해석 금지 재확인.** *"최근 감정 기록 평균보다 오늘 값이 낮았어요"*는
사실이고 *"힘드시겠어요"*는 금지다. 원인을 절대 말하지 않는다. 기존 조언·인과
블록리스트를 그대로 적용한다.

## 3. 확인을 뒤집는다 — opt-in → opt-out

지금은 **사용자가 [맞아요]를 눌러야** 일기에 차이가 들어간다. 안 누르면 아무 일도
일어나지 않는다. *"당신의 피드백이 정확도를 높입니다"* 는 **회사 사정이지
사용자 이득이 아니다.**

| | 지금 | 바꾼 뒤 |
|---|---|---|
| 일기에 반영 | `status='confirmed'` 만 | **`status != 'dismissed'`** |
| 사용자 행동 | 맞아요를 눌러야 함 | **틀렸을 때만 [아니에요]** |

노동이 사라지고, 기각 데이터가 오히려 정직해진다 — "귀찮아서 안 누른 것"과
"진짜 맞는 것"이 더는 섞이지 않는다.

[맞아요] 버튼은 **남긴다**(잘 찾았다는 신호는 받을 가치가 있다). 다만 그것이
**관문이 아니게** 한다.

opt-out이 허용되는 전제는 차이 문장이 생활을 추측하지 않고 **기록에서 계산된
사실로만 한정**되는 것이다. 후보 상태의 차이를 일기에 넣을 때도
*"최근 기록에서"*라는 범위를 유지한다. 이 가드레일을 통과하지 못한 후보는
사용자 확인 여부와 관계없이 일기에 들어가지 않는다.

### 기각 학습

```
표시점수 = 놀라움 ÷ (1 + 최근 28일의 같은 엔티티·method 기각 횟수)
최근 28일에 기각 3회 이상 → 이번 후보 제외
```

영구 제외는 사용자의 관심이 바뀔 수 있다는 사실을 무시하므로 쓰지 않는다.
`differences` 테이블의 `date`와 `status`에서 계산할 수 있다.

## 5. MVP 범위 — 화면 7개

와이어프레임 7화면을 전부 만든다. 단 **동작하지 않는 것은 그리지 않는다.**

| # | 화면 | 경로 | 이번 범위 |
|---|---|---|---|
| 1 | 오늘(홈) | `/` | **발견 우선으로 재구성** + 하단 탭바 |
| 2 | 기록 | `/record` | 텍스트 · 감정칩. 사진·음성·위치는 **뺀다** |
| 3 | 일기 | `/diary` | 기존 + **기본 프리셋·1회 빠른/자유 주문** |
| 4 | 차이 확인 | `/review` | 기존 + 근거 표시 · opt-out |
| 5 | 주간 리포트 | `/report` | **신규** |
| 6 | 회고 | `/recall` | **신규 — 키워드 검색** |
| 7 | 설정·데이터 | `/settings` | 톤 + **내보내기 · 전체 삭제** |

### 뺀 것과 그 이유

| 뺀 것 | 이유 |
|---|---|
| **사진 입력** | Storage 기반만 있고 업로드 UI·압축·실패 복구가 없다. 별도 기능으로 완성하기 전엔 버튼을 두지 않는다 |
| **음성 · 위치 입력** | STT·센서 수집이 없다. 버튼만 두면 **거짓 약속**이다 |
| **걸음 · 방문장소 동의 토글** | 수집하는 코드가 없다. 켜도 아무 일이 안 일어난다 |
| **벡터 회고(RAG)** | `embeddings` 테이블이 없다. 메모 수백 건에선 **키워드 검색이 실제로 잘 된다.** 벡터는 규모가 생긴 뒤 |
| **시간축**(*"40분 일찍 퇴근"*) | `captured_at`만으론 "퇴근"이라는 사건을 모른다. 센서나 구조화 입력이 필요 |
| **공유 카드** | 리포트가 먼저 쓸 만해야 공유할 것이 생긴다 |

## 6. 자동 일기 — 상태 문구

> **v3 갱신(2026-07-28).** v2는 "잡 상태가 없으므로 생성 중·실패를 화면에서
> 추측하지 않는다"고 적었다. Phase 0~1 구현에서 **`diary_generation_requests`
> 원장을 실제로 만들었으므로** 그 전제가 사라졌다. 아래가 현재 사실이다.

일기는 **Day 0 보상**인데(§0) 생성 경로가 CLI뿐이면 웹 사용자는 첫날 받을 것이
없다. 그래서 **웹에서 직접 생성을 요청**할 수 있게 하고, 그 요청을 추측이 아니라
**원장으로 관측**한다(ADR-0003).

| 상태 | 홈 표시 |
|---|---|
| 기록 없음 | "오늘은 아직 조용하네요" |
| 생성 가능 | "오늘 기록으로 일기를 만들 수 있어요" + [오늘 일기 만들기] |
| 마감 시간 | "오늘을 정리할 시간이에요" |
| 차이 발견 | "기록에서 눈에 띄는 차이를 찾았어요" |
| 생성 요청(`queued`) | "일기 만들기를 요청했어요" |
| 워커 처리 중(`processing`) | "오늘 기록을 한 편으로 묶고 있어요" |
| 완료(`done`) | `DAILY WRAP` · "오늘의 일기가 도착했어요" + 열어보기 |
| 실패(`failed`) | "일기를 만들지 못했어요" + 다시 시도 |

문구는 **제안형**이다. "하루가 끝났다"처럼 단정하지 않는다.

- 요청은 **`(user_id, date)` 유니크로 멱등**하다. 연타가 잡을 늘리지 않는다
- 앱은 원장과 큐에만 쓰고, **LLM 호출은 워커가 한다**(2자산 경계 유지)
- 이미 일기가 있으면 요청은 즉시 `done`으로 수렴한다
- 오늘 메모가 없으면 **적재 자체를 거부**한다(`memory_required`)
- `failed`는 다시 요청하면 `queued`로 되돌아간다

**자동 재생성은 없다.** 늦게 남긴 메모는 사용자가 "다시 만들기"를 눌러야 반영된다.

### 아직 없는 것 — 베타 운영 게이트

**야간 자동 실행과 알림은 여전히 없다.** 지금은 사람이 버튼을 누르거나 CLI를
돌려야 한다. 위 상태 표가 채워졌다고 **"자동 일기 운영 완료"라고 선언하지 않는다.**
스케줄러·알림·PWA는 별도 게이트다.

## 7. 성공 지표 — 잴 수 있는 것만

분석 인프라가 없다. **SQL 한 번으로 나오는 4개만** 정하고 `stats` 명령으로 찍는다.

| 지표 | 산식 | 목표 |
|---|---|---|
| **명시적 긍정 비율** | `confirmed / (confirmed + dismissed)` | 표본 20건 전에는 참고만 |
| 하루 노출 차이 수 | 카드 수 / 활동일 | 1~3 |
| 일기 확정률 | `confirmed diaries / 전체` | — |
| 3일·7일 도달자 수 | 관측일수 분포 | — |

opt-out에서는 아무 행동도 하지 않은 후보가 분모에서 빠지므로 이 비율을
"정확도"라고 부르지 않는다. 카드 노출 로그가 생기기 전에는 방향성 지표일 뿐이다.
재방문율·알림 해제율·근거 열람률은 측정 수단이 생길 때 추가한다.

## 9. 스키마 변경 — 최소 마이그레이션 2건

화면과 엔티티 차이는 기존 스키마로 구현할 수 있다. 다만 감정 차이는
`entity_id is null`이고, 현재 유니크 인덱스는 `entity_id is not null`인 차이만
보호한다. 그대로 저장하면 워커 재실행이 감정 차이를 중복 생성한다.

따라서 아래 부분 유니크 인덱스와 down 마이그레이션이 필요하다.

```sql
create unique index differences_dimension_natural_key
  on public.differences (user_id, date, dimension, detection_method)
  where entity_id is null;
```

또한 `deletions`는 의도적으로 authenticated 쓰기가 막혀 있다. 앱에 service role을
노출하지 않고 삭제 요청을 만들려면 `auth.uid()`만 사용하는
`security definer request_account_data_deletion()` RPC와 down 마이그레이션이
필요하다. 새 테이블·컬럼은 아니지만 DB 마이그레이션은 맞다.

| 필요한 것 | 이미 있는 것 |
|---|---|
| 놀라움 점수 | `differences.confidence` (real) |
| 부재 | `detection_method='freq_shift'` 재사용 |
| 감정축의 값 | `detection_method='zscore'` · `category='감정전환'` |
| 주간 리포트 | `weekly_reports` · `weekly_report_highlights` |
| 기각 학습 | `differences.status` 카운트 |
| 회고 검색 | `memories.raw_text` |

`weekly_report_highlights`는 텍스트를 직접 담지 않고 `difference_id`를 요구한다.
따라서 최다 빈도·감정 순간도 deterministic `pattern`/`zscore` difference로 먼저
저장하고 evidence를 연결한 뒤 하이라이트가 참조한다.

## 10. 베타 운영 게이트

와이어프레임 7화면과 실제 운영 가능 상태는 같지 않다. 다음은 화면 구현 뒤에도

- 삭제 파이프라인 보안 리뷰와 사람 주도 파괴 테스트
- 안전하게 격리된 전체 통합 테스트

## 11. 불변 원칙 재확인

이 설계는 아래를 **하나도 깨지 않는다.**

- 탐지는 통계(놀라움·z-score), 서술만 LLM
- LLM은 사실·행동·장소·감정·인과를 추측하지 않음 — 감정축도 **사실만** 말한다
- 모든 출력에 evidence ID
- 스트릭·진행률·죄책감 UI 없음 — 계단식 개방은 **약속이지 압박이 아니다**
- 사용자 기록 본문을 로그·커밋에 남기지 않음
